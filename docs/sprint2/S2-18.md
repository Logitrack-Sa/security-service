- **Estimación:** 5 puntos Fibonacci
- **Estado:** Completada y verificada

## 1. Resumen y Objetivo

Construir una suite de seguridad integral (positiva y negativa) reutilizable como fixtures de contrato para todo el ecosistema de microservicios de LogiTrack (`security-service`, `courier-service`, `shipment-service`), asegurando que ningún microservicio comparta lógica de dominio, tablas ni entidades JPA.

La entrega establece y verifica las garantías criptográficas y de autorización acordadas en el contrato del Sprint 2:
1. Rechazo estandarizado (401 Unauthorized) ante cualquier anomalía o manipulación en tokens JWT (vencimiento, firma manipulada, algoritmo inadecuado, emisor o audiencia inválidos, ausencia de token).
2. Protección inviolable del registro público (exclusivamente rol `CLIENTE`, rechazo estricto de escalación o pre-asignación de identidades de dominio `customerId`/`courierId`).
3. Verificación de la matriz de autorización y aislamiento total entre identidades canónicas de dominio (2 Clientes y 2 Repartidores).
4. Garantía de validación descentralizada 100% autónoma y offline sin dependencia de red HTTP hacia el emisor durante las peticiones a endpoints protegidos.

## 2. Criterios de Aceptación y Solución Implementada

### 2.1 Batería de pruebas negativas y casos de borde de JWT
Se implementó en `SecurityConfiguration` un validador compuesto delegativo (`DelegatingOAuth2TokenValidator`) que combina:
- `JwtValidators.createDefaultWithIssuer(jwtProperties.issuer())`: Valida ventana temporal (`nbf`, `iat`, `exp`) y claim `iss`.
- `algorithmValidator`: Exige cabecera `alg: RS256` y rechaza cualquier algoritmo no asimétrico o no permitido (como `HS256` simétrico o `none`).
- `audienceValidator`: Exige que el claim `aud` esté presente y contenga una audiencia autorizada en las propiedades del servicio (`security-service`, `courier-service`, `shipment-service`).
- `NimbusJwtDecoder.withPublicKey(...)`: Comprueba la firma criptográfica RSA contra la clave pública del servicio emisor.
- `AuthenticationEntryPoint` estandarizado: Intercepta fallos de autenticación y emite respuestas JSON `401 Unauthorized` con código `UNAUTHORIZED`.

### 2.2 Registro público sin escalación de privilegios
- El endpoint `POST /api/v1/auth/register` crea estrictamente usuarios con rol `CLIENTE`.
- Si el solicitante intenta inyectar campos privilegiados como `roles: ["ADMIN"]`, `role: "REPARTIDOR"`, o vínculos de dominio `customerId` / `courierId`, la solicitud es rechazada de inmediato con `400 Bad Request` (`PRIVILEGE_ESCALATION` o `VALIDATION_ERROR`).
- Los vínculos `customerId` y `courierId` se gestionan únicamente por administradores autenticados (`ROLE_ADMIN`) a través de las rutas protegidas `/api/v1/users/{id}/*-link`.
- El administrador tiene prohibido auto-modificar arbitrariamente sus propios roles, evitando bloqueos accidentales o escalaciones forzadas.

### 2.3 Matriz de identidades canónicas y aislamiento de dominio
Se publicó el archivo fixture de contrato canónico `src/test/resources/contracts/v1/identities.json`, compuesto por 5 identidades fijas:
- **`admin`**: Usuario con rol `ADMIN`, capaz de gestionar perfiles e identidades de cualquier usuario.
- **`cliente-a`**: Usuario con rol `CLIENTE` vinculado al `customerId` `10000000-0000-0000-0000-000000000001`.
- **`cliente-b`**: Usuario con rol `CLIENTE` vinculado al `customerId` `10000000-0000-0000-0000-000000000002`.
- **`repartidor-a`**: Usuario con rol `REPARTIDOR` vinculado al `courierId` `20000000-0000-0000-0000-000000000001`.
- **`repartidor-b`**: Usuario con rol `REPARTIDOR` vinculado al `courierId` `20000000-0000-0000-0000-000000000002`.

#### Matriz de Comportamiento Verificada en Pruebas
| Operación / Endpoint | ADMIN | CLIENTE A | CLIENTE B | REPARTIDOR A | REPARTIDOR B |
|---|---|---|---|---|---|
| `GET /api/v1/auth/me` | 200 OK (datos admin) | 200 OK (datos propios, customerId A) | 200 OK (datos propios, customerId B) | 200 OK (datos propios, courierId A) | 200 OK (datos propios, courierId B) |

| `POST /api/v1/auth/register` (público) | Crea CLIENTE | Crea CLIENTE | Crea CLIENTE | Crea CLIENTE | Crea CLIENTE |

### 2.4 Verificación descentralizada sin dependencia HTTP
- Se comprobó que el decodificador de tokens en memoria (`NimbusJwtDecoder`) no establece conexiones de red salientes al emisor para validar firmas ni claims.
- La verificación de firma se realiza de forma local mediante la clave pública RSA (inyectada por archivo PEM o configuración).
- Los servicios consumidores (`courier-service` y `shipment-service`) consumen de forma idéntica las identidades de fixture y la clave pública sin acoplamiento en tiempo de ejecución.

## 4. Evidencia de Pruebas y Resultados de Ejecución

### 4.1 Suite Dedicada `JwtRolesAndIdentityIsolationTest`
Se implementaron 26 pruebas organizadas por criterios de aceptación:
- **Criterio 1: JWT negativo y casos de borde (10 pruebas):**
  - `1.1 Token JWT expirado responde 401 Unauthorized`
  - `1.2 Token JWT con firma criptográfica alterada responde 401 Unauthorized`
  - `1.3 Token JWT firmado con clave RSA foránea no confiable responde 401 Unauthorized`
  - `1.4 Token JWT con algoritmo simétrico HS256 es rechazado con 401 Unauthorized`
  - `1.5 Token JWT sin firma (algoritmo none) es rechazado con 401 Unauthorized`
  - `1.6 Token JWT con emisor (iss) ajeno o falso responde 401 Unauthorized`
  - `1.7 Token JWT con audiencia (aud) no autorizada responde 401 Unauthorized`
  - `1.8 Token JWT sin claim de audiencia responde 401 Unauthorized`
  - `1.9 Petición a endpoint protegido sin token responde 401 Unauthorized`
  - `1.10 Petición con valor Bearer malformado responde 401 Unauthorized`
- **Criterio 2: Registro público y prevención de escalación (6 pruebas):**
  - `2.1 Registro público crea exclusivamente usuario con rol CLIENTE`
  - `2.2 Intento de inyectar roles privilegiados en registro público devuelve 400 Bad Request`
  - `2.3 Intento de inyectar vínculos de dominio en registro público devuelve 400 Bad Request`
  - `2.4 CLIENTE recibe 403 Forbidden al intentar acceder a rutas de administración de usuarios`
  - `2.5 REPARTIDOR recibe 403 Forbidden al intentar vincular identidades de cliente`
  - `2.6 ADMIN no puede auto-modificar arbitrariamente sus propios roles (400 PRIVILEGE_ESCALATION)`
- **Criterio 3: Matriz para 2 Clientes y 2 Repartidores y aislamiento estricto (8 pruebas):**
  - `3.1 Cliente A accede a GET /api/v1/auth/me y obtiene su customerId asignado`
  - `3.2 Cliente B accede a GET /api/v1/auth/me y obtiene su customerId asignado (aislado de Cliente A)`
  - `3.3 Cliente A recibe 403 Forbidden al intentar consultar al Cliente B`
  - `3.4 Repartidor A accede a GET /api/v1/auth/me y obtiene su courierId asignado`
  - `3.5 Repartidor B accede a GET /api/v1/auth/me y obtiene su courierId asignado (aislado de Repartidor A)`
  - `3.6 Repartidor A recibe 403 Forbidden al intentar consultar al Repartidor B`
  - `3.7 ADMIN puede consultar perfiles de cualquier cliente o repartidor en /api/v1/users/{id}`
  - `3.8 ADMIN puede vincular o actualizar identidades de dominio en usuarios objetivo`
- **Criterio 4: Validación descentralizada sin dependencia HTTP (2 pruebas):**
  - `4.1 La validación del JWT se ejecuta localmente mediante la clave pública sin llamadas HTTP`
  - `4.2 Endpoint protegido valida la identidad localmente sin interactuar con servicios externos`
