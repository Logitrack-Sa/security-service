# S2-12: Registrar usuarios y vincular identidades sin elevar privilegios

## 1. Resumen y Objetivo

Implementar el registro público de usuarios (`POST /api/v1/auth/register`) garantizando el almacenamiento de contraseñas hasheadas mediante `PasswordEncoder` (BCrypt). Prohibir de manera estricta la autoasignación de roles privilegiados (`ADMIN`, `REPARTIDOR`) o identidades de dominio ajenas (`customerId`, `courierId`) en el payload de registro público.

Definir un mecanismo seguro de entorno para la provisión del `ADMIN` inicial y reservar las altas privilegiadas y vinculaciones de dominio exclusivamente a administradores autenticados mediante los endpoints `/api/v1/users/**`.

---

## 2. Criterios de Aceptación y Solución Implementada

### 2.1 Registro público solo permite CLIENTE (Prevención de escalación)
- **Endpoint:** `POST /api/v1/auth/register` (público, no requiere autenticación previa).
- **Rol asignado:** Exclusivamente `Role.CLIENTE`.
- **Reglas de escalación:** Si en el cuerpo de la solicitud se incluye:
  - `role` con valor distinto de `CLIENTE` (ej. `ADMIN`, `REPARTIDOR`).
  - `roles` con cualquier rol que no sea exclusivamente `CLIENTE`.
  - `customerId` o `courierId` con algún valor no nulo.
  La solicitud es inmediatamente rechazada con **`400 Bad Request`** y código funcional `PRIVILEGE_ESCALATION` a través de `PrivilegeEscalationException` y `GlobalExceptionHandler`.
- En caso de éxito, responde **`201 Created`** con la cabecera `Location: /api/v1/users/{id}` y el DTO `UserResponse`.

### 2.2 Provisión de ADMIN inicial por entorno y operaciones administrativas protegidas
- **Provisión de ADMIN inicial:** Implementado en `AdminBootstrap` (`ApplicationRunner`) y parametrizado vía `AdminProperties` (`security.admin.*`).
  - Variables de entorno: `SECURITY_ADMIN_ENABLED`, `SECURITY_ADMIN_USERNAME`, `SECURITY_ADMIN_EMAIL`, `SECURITY_ADMIN_PASSWORD`.
  - La contraseña nunca se almacena en plano ni se loguea; se genera un hash BCrypt al persistir la cuenta.
  - La provisión es idempotente: si el usuario ya existe en base de datos, no se duplica ni altera.
- **Protección de endpoints administrativos:**
  - Rutas bajo `/api/v1/users/**` aseguradas en `SecurityConfiguration` con `.hasRole("ADMIN")`.
  - Sin JWT válido se devuelve **401**; con rol `CLIENTE` o `REPARTIDOR` se devuelve **403**.

### 2.3 Persistencia y unicidad de vínculos de dominio (`customerId` y `courierId`)
- **Separación de identidades:** El UUID del usuario (`id`) representa al sujeto de autenticación y es independiente de los identificadores de dominio (`customerId` en `shipment-service` y `courierId` en `courier-service`).
- **Migración de esquema:** `V2__identities_and_usernames.sql` agrega las columnas `customer_id` y `courier_id` de tipo `BINARY(16)` con restricciones de unicidad (`uk_users_customer_id` y `uk_users_courier_id`), además de `username` y `name`.
- **Vínculos confiables:** Solo un `ADMIN` autenticado puede asociar o modificar `customerId` o `courierId`. Si se intenta asociar un identificador de dominio ya vinculado a otro usuario, la petición se rechaza con **`409 Conflict`** (`DUPLICATE_RESOURCE`).

### 2.4 Seguridad de contraseñas, hashes y códigos de respuesta
- **Hashes seguros:** Contraseñas codificadas mediante `BCryptPasswordEncoder`. La entidad `User` posee `@JsonIgnore` sobre `passwordHash`.
- **Nunca en respuestas:** El DTO inmutable `UserResponse` expone únicamente `id`, `email`, `username`, `name`, `roles`, `enabled`, `customerId` y `courierId`. Ni contraseñas ni hashes aparecen en las respuestas HTTP ni en registros de auditoría o logs.
- **Códigos HTTP aplicados:**
  - `201 Created`: Creación exitosa de usuario.
  - `200 OK`: Consulta o actualización exitosa de usuario/roles/vínculos.
  - `400 Bad Request`: Payload mal formado, datos inválidos (`VALIDATION_ERROR`) o escalación de privilegios (`PRIVILEGE_ESCALATION`).
  - `403 Forbidden`: Falta de rol requerido (`ADMIN`); sin JWT válido se devuelve 401.
  - `404 Not Found`: Usuario o recurso solicitado inexistente (`RESOURCE_NOT_FOUND`).
  - `409 Conflict`: Conflicto por duplicidad de email, username, customerId o courierId (`DUPLICATE_RESOURCE` / `DATA_CONFLICT`).

## 3. Especificación de Endpoints

### 3.1 Registro Público
- **`POST /api/v1/auth/register`**
  - **Acceso:** Público (anónimo permitido).
  - **Cuerpo:**
    ```json
    {
      "email": "cliente@logitrack.com",
      "password": "Password123!",
      "username": "cliente_demo",
      "name": "Cliente Demo"
    }
    ```
  - **Respuesta (201 Created):**
    ```json
    {
      "id": "c1f7b830-4e2a-4f51-b88a-2c813589b910",
      "email": "cliente@logitrack.com",
      "username": "cliente_demo",
      "name": "Cliente Demo",
      "roles": ["CLIENTE"],
      "enabled": true,
      "customerId": null,
      "courierId": null
    }
    ```

### 3.2 Administración de Usuarios (Exclusivo ADMIN)
- **`POST /api/v1/users`**
  - **Acceso:** Autenticado con `ROLE_ADMIN`.
  - **Cuerpo:** Permite especificar roles (`ADMIN`, `CLIENTE`, `REPARTIDOR`) y vínculos de dominio:
    ```json
    {
      "email": "repartidor@logitrack.com",
      "password": "Repartidor123!",
      "username": "repartidor_demo",
      "name": "Repartidor Demo",
      "roles": ["REPARTIDOR"],
      "courierId": "5f009c21-3f73-4805-ac30-44171fa74a42"
    }
    ```
- **`GET /api/v1/users/{id}`**
  - **Acceso:** Autenticado con `ROLE_ADMIN`.
  - **Respuesta (200 OK):** `UserResponse`.
- **`PUT /api/v1/users/{id}/roles` y `PATCH /api/v1/users/{id}/roles`**
  - **Acceso:** Autenticado con `ROLE_ADMIN`.
  - **Cuerpo:** `{"roles": ["REPARTIDOR"]}`.
- **`PUT /api/v1/users/{id}/customer-link` y `PATCH /api/v1/users/{id}/customer-link`**
  - **Acceso:** Autenticado con `ROLE_ADMIN`.
  - **Cuerpo:** `{"customerId": "c4c9e0f5-72e1-4836-bab4-0ce9db3c41c9"}`.
- **`PUT /api/v1/users/{id}/courier-link` y `PATCH /api/v1/users/{id}/courier-link`**
  - **Acceso:** Autenticado con `ROLE_ADMIN`.
  - **Cuerpo:** `{"courierId": "5f009c21-3f73-4805-ac30-44171fa74a42"}`.
